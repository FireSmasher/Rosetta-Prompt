Example use cases per effort level, from `build-with-claude/effort` (cached 5 Sep 2026 in `model-selection.md` in this folder; re-read 25 Sep 2026, unchanged except that `high` is now "the default on every model that supports effort except Claude Opus 5.5"): `low` for "simpler tasks that need the best speed and lowest costs, such as subagents"; `medium` for "agentic tasks that require a balance of speed, cost, and performance"; `high` for "complex reasoning, difficult coding problems, agentic tasks" (the default); `xhigh` for "long-running agentic and coding tasks (over 30 minutes) with token budgets in the millions"; `max` for "tasks requiring the deepest possible reasoning and most thorough analysis." ## Migration notes between models

What changes for someone pasting in a prompt written for an earlier model. Mechanical API changes (thinking-block plumbing, tool versions, sampling parameter restrictions) are left out on purpose, matching this file's stated scope; only points that would change how you'd write the prompt text are kept.

- **Fable 5 to Fable 5.1** (`models/fable-5-1/migration-guide`): same input/output price, cache reads a quarter of the cost. Behavior carries the three points already in the Fable 5.1 section below (fewer parallel tool calls unless batching is requested, fewer progress updates unless asked for, less searching at `low` effort on half-recognized names).
- **Opus 5 to Opus 5.5** (`models/opus-5-5/migration-guide`, `whats-new-opus-5-5`, 24 Sep 2026): cheaper per token ($4/$20 against $5/$25), output more than 30% faster, and it tends to finish the same task with fewer tokens; Anthropic says prompts written for Opus 5 "should perform well without changes." What changes for prompt text: the default effort is now `medium`, so state the level a task needs rather than relying on the default; at a given level it thinks more per turn than Opus 5; thinking can no longer be disabled, so instructions written as a substitute for thinking should go; instructions tuned to Opus 5's quirks "may no longer be needed" and are worth re-testing rather than carrying over blindly; and when a tool applies, say so in the prompt, since forcing a tool call is no longer possible.
- **Opus 4.8 to Opus 5** (`models/opus-5/migration-guide`, `models/opus-5/whats-new-opus-5`): same per-token price as Opus 4.8. Thinking is now on by default. Default visible responses and written deliverables run longer than on Opus 4.8, so a prompt tuned for 4.8's shorter defaults needs an explicit conciseness or length instruction, not a carried-over assumption. Carried-over "double-check" or "verify before responding" instructions cause over-verification on Opus 5 and should be dropped rather than kept. Opus 5 delegates to subagents more readily than Opus 4.8, so multi-agent prompts should say when delegation is warranted or cap the count.
- **Opus 4.6 to Opus 4.7 (carried forward into Opus 5)** (`models/opus-5/migration-guide`): more literal instruction following, especially at low effort, so a prompt can no longer rely on the model generalizing one example to the rest; state scope explicitly. Stricter effort calibration: at `low`/`medium` the model scopes tightly and can under-think a moderately complex task, so raise effort rather than prompt around it if reasoning looks shallow.
- **Sonnet 4.6 to Sonnet 5** (`models/sonnet-5/migration-guide`): a new tokenizer means the same input text produces about 30% more tokens than on Sonnet 4.6, so a `max_tokens` tuned for 4.6 can truncate equivalent output and the 1M context window holds less text than before, in tokens. Per-token price dropped ($2/$10 versus Sonnet 4.6's $3/$15), but because of the token-count increase the cost of an equivalent request does not drop in direct proportion. Thinking is on by default now, same as the Opus jump.
- **Haiku 3.5 to Haiku 4.5** (`models/haiku-4-5/migration-guide`): output capacity rose to 64K tokens, and it gained context awareness (tracks its own remaining window, see the Haiku 4.5 section below). Communication style shifted more concise and direct, same general-model direction as the other 4.x jumps, so prompts written for Haiku 3.5's chattier defaults may need a length or tone instruction where none was needed before.

## Cost versus intelligence (from `optimizing-for-cost-and-intelligence`)

This informs how this skill picks a target and an effort level; it is not itself a prompting technique.

- **Effort before model.** Sweep effort on the current model first, it's the cheapest experiment; only change model on a genuine two-class-or-more mismatch. `model-selection.md` in this folder already encodes this as "the order of levers," sourced 5 Sep 2026 from the same page; re-read 16 Sep 2026, the guidance is unchanged, only the supporting benchmark numbers are more detailed than what's quoted there.
- **Compare cost per completed task, never cost per token.** Per token the frontier model looks several times pricier, but a more capable model often finishes in fewer turns with less backtracking, which can make it cheaper per solved task. Example from the doc: Fable 5.1 at `low` solved 88.6% of a SWE-bench Pro subset for $0.54 per solved task versus Sonnet 5 at default solving 77.4% for $0.84, eleven more points for 35% less, despite a five-times-higher per-token price. It doesn't always flip that way: Opus 5.5 at its default (`medium`) matched Fable 5.1 at its default on the same subset for about a fifth of the cost per solved task (24 Sep 2026 read; the 16 Sep read gave Opus 5 about 15% less). Anthropic's current default advice: "For most agent workloads, start with Claude Opus 5.5 at its default effort (`medium`), and use Claude Fable 5.1 for demanding reasoning and long-horizon agentic work, or when your evals on Claude Opus 5.5 at higher effort still fall short."
- **Price the tail, not the median.** On one 20-task benchmark run, the two costliest tasks carried 43% of total spend. Every model looks similar and cheap on typical tasks; the bill is decided by the hardest tenth, where a cheap model's failed attempt still bills tokens, then the retry, then the downstream cost of the failure.
- **Re-run failures at higher effort, rather than running everything at high effort.** When a task's outcome is checkable, running every task at a low setting and only re-running the failures at a higher one beats a fixed high setting, and beats reaching for a second model. Opus 5.5 figures: at `low`, 13% of tasks failed; re-running those at `high` passed about 97% for about $0.17 a task, against 95.3% for $0.29 running everything at `high`, and starting at `medium` instead solved about 97% for about $0.24.
- **Opus 5.5 beats Fable 5.1 per dollar on narrower work too.** Chart reading: Opus 5.5 at `low` scored 68.7 for about $0.03 a chart, against 62.5 for $0.15 from Fable 5.1 at `low`. Anthropic's capability-first path: implement with Opus 5.5, lower effort or model once evals allow, and move to Fable 5.1 only "if your evals at xhigh or max effort still fall short on demanding reasoning or long-horizon agentic work" (`choosing-a-model`).
- **Not every hard task needs high effort.** On one long-research benchmark, Fable 5.1 scored nearly the same at `low`, `medium`, and `high` while cost per task rose from $4.66 to $7.12; raising effort bought no measurable quality there. Long-horizon coding is the case where effort reliably buys accuracy (measured against `high` on SWE-bench Pro, 25 Sep 2026 read: Opus 5.5 "scored about 2.5 points lower at its default, medium, for about 70% of the cost, and about 8 points lower at low for about a third of the cost; xhigh scored about 1.4 points higher for 2.5 times the cost of high"). The task description alone doesn't reveal which kind of workload a given prompt sits in, hence Anthropic's advice to sweep two or three effort levels on real traffic rather than guess from the task's apparent difficulty.

**Scope.** This file grounds `/rosetta-prompt` rewrites of a single well-formed chat or CLI prompt, not API integration mechanics (tool-result plumbing, thinking-block replay, append-only history, turn-scoped system messages, `budget_tokens` migration, prefill removal, `max_tokens` headroom, sampling parameters, parallel tool call JSON). Where a source technique is really an API or harness change rather than something you'd write into prompt text, it is left out on purpose.

Use "General principles" for any Claude target, plus only the section matching the chosen target. Don't pull in the other model sections.

## General principles (all current Claude models)

1. **Be clear and direct.** Claude is a brilliant new employee with no context on your norms. State desired output format, constraints, and any "above and beyond" behavior explicitly. Golden rule: if a colleague with minimal context would be confused by the prompt, so will Claude. Use numbered steps or bullets when order or completeness matters.
2. **Add context and motivation, not just the instruction.** Explaining why a constraint exists ("read aloud by text to speech, so no ellipses") lets Claude generalize correctly instead of pattern matching the literal rule.
3. **Use examples (multishot).** 3 to 5 well chosen examples is one of the most reliable levers on format, tone, and structure. Make them relevant, diverse (cover edge cases, vary enough that Claude doesn't copy unintended patterns), and wrapped in `<example>`/`<examples>` tags.
4. **Structure with XML tags** when a prompt mixes instructions, context, examples, and variable input: `<instructions>`, `<context>`, `<input>`. Consistent, descriptive tag names; nest when content has real hierarchy (`<documents>` holding `<document index="n">`). Most valuable for long or mixed-content prompts, not a short single ask.
5. **Give Claude a role** when a persona or domain lens sharpens the response. Even one sentence helps. Skip it when the task doesn't need one.
6. **Long context prompts (20k+ tokens):** put the long document(s) at the top, above the instructions, examples and query; a query at the end can improve quality by up to 30% on complex multi-document input. Wrap each document in `<document><source>...</source><document_content>...</document_content></document>`. For grounded analysis, ask Claude to quote the relevant passages first (in `<quotes>` tags), then work from them.
7. **Say what you want, not just what you don't.** "Do not use markdown" is weaker than "write in smoothly flowing prose paragraphs." Matching the prompt's own style to the desired output also steers format (less markdown in the prompt, less in the output). If plain-text math is needed, say so explicitly, since current models default to LaTeX.
8. **Tool or action framing:** if the goal is for Claude to actually do something, say so as an action ("change this function to improve performance"), not a suggestion ("can you suggest some changes"); current models follow the literal ask. If a task should default to acting without asking, or conversely to research and recommendations without editing anything, say which. Use normal language ("use this tool when...") rather than "CRITICAL: you MUST", which now over-triggers.
9. **Communication style defaults leaner.** Current models are more direct, more conversational, and may skip summaries after tool calls. If visibility matters, ask for a quick summary after tool use. Opus 5.5 is the exception (runs longer, carried over from Opus 5) and Fable 5.1 writes fewer updates during agentic work; see their sections.
10. **For agentic or coding tasks, name the scope discipline you want.** Unprompted, models can add unrequested features, abstractions, defensive code, docstrings or helper scripts. A short instruction fixes this: only make changes that are requested or clearly necessary, no error handling for scenarios that can't happen, no abstractions for one-time operations. For coding, ask for a general solution rather than one that hard-codes test cases, and to say so if a test looks wrong.
11. **For research or fact-heavy tasks, state what a successful answer looks like and ask for verification across multiple sources.** For complex research, ask for competing hypotheses and tracked confidence.
12. **For agentic tasks touching real systems, name what's reversible and what isn't.** Local, reversible actions (editing files, running tests) can proceed; destructive, hard-to-reverse, or visible-to-others actions (deleting, force-pushing, posting, sending) should pause for confirmation. Don't let obstacles justify destructive shortcuts. For code questions, tell the model never to speculate about code it has not opened.
13. **For thinking tasks, prefer a general instruction to reason carefully over a prescriptive step-by-step plan.** Claude's own reasoning usually beats a hand-written checklist. Asking Claude to verify against stated criteria before finishing catches errors reliably, except on Opus 5.5 (see its section). If a model is thinking more than a simple task needs, say thinking should be reserved for problems that need multistep reasoning and to respond directly when in doubt.
14. **Guardrail: allow uncertainty and ground claims (reduce hallucinations).** When a prompt asks for facts, analysis of provided material, or advice, give explicit permission to say "I don't have enough information" rather than guess. For long documents, have Claude extract word-for-word quotes first and base the answer only on them. Where auditability matters, ask for a supporting quote or source per claim, and to retract any claim it can't support. If the answer must come only from provided material, say so ("use only these documents, not general knowledge"). Only add these where the task actually carries a factual risk.
15. **Guardrail: make repeatable outputs consistent.** When output feeds a repeated process or must keep a fixed shape, define the format precisely (a JSON key list, an XML template) and show an example of the exact output. For answers that must stay consistent with a knowledge base, put the reference entries in the prompt and tell Claude to check them first. For a persona, describe its traits and list the common scenarios with how to handle each. Prefill is not available on current models, so use format instructions and examples instead.
16. **Guardrail: prompt leak, only when it matters.** Don't put secrets, credentials, or private details in a prompt unless the task needs them; leaving them out is the most reliable protection. If a prompt must keep something from end users, one plain instruction is enough; elaborate leak-proofing adds complexity that degrades the main task, and Anthropic advises it only when absolutely necessary.

## Fable 5.1-specific notes

Current flagship. Existing Fable 5 prompts carry over; these are the behaviors that differ, worth encoding when relevant:

- **Effort is the main quality/cost/latency dial**, not a prompting technique. Default `high`; `medium` roughly matches Fable 5 at lower cost; `low` is often competitive with Opus and Sonnet on cost per task while scoring higher; `xhigh`/`max` only where a gain is measured. Effort is set by the caller, but flag the level a task's difficulty suggests.
- **Writes fewer user-facing updates during long tool-calling work.** Remove any "hold all findings for the final response" style line first. If updates are wanted: say in a line what it's about to do before starting, give brief updates while working, and close with a short self-contained recap (what was found, what was done, what's next) so a reader of only the last message has the full picture. If the UI hides tool output, tell it to put anything the user needs to read into its reply.
- **Batches implied tool calls less in coding and computer-use loops.** For those, one line helps: first privately list what's needed next, then request every item that doesn't depend on another's result in one response.
- **Prose can run dense** (long sentences, few paragraph breaks) and slide into mannered writing. For writing tasks, add a short anti-mannered-prose rule: say what you mean and use the literal phrase when one is available, not metaphor or flourish. "Please remove all mannered prose" alone also tends to work.
- **Under-formats in chat** (less bold, fewer headers and lists). Remove blanket anti-formatting rules; instead say when structure is appropriate: lists when asked or when content is multifaceted, no lists or headers when minimal formatting is requested, plain prose in conversational or emotional exchanges.
- **Can reproduce source wording unmarked when summarizing.** For summaries of documents or search results, include one complete example of a correct response (request, response, and why it is correct) showing sources paraphrased in its own words with any short verbatim phrase marked as a quote.
- **Can end a turn early**, describing a next step instead of doing it, or asking permission already implied. For autonomous tasks: the user isn't watching and can't answer mid-task, so proceed with reversible actions that follow from the request, stop only for destructive actions or genuine scope changes, and before ending check that the last paragraph isn't an undone plan or promise. Exception to state: when the user is only describing a problem or asking a question, the deliverable is the assessment, not a fix.
- **Can widen or narrow scope.** The request sets the scope: make routine judgment calls, check in only when readings would lead to materially different work, raise a real concern in a sentence and keep building, do everything that doesn't depend on an open question first, and list anything blocked rather than silently scaling down.
- **Can over-deliver on open-ended features** (fixing nearby code, extra tests). For a tightly scoped task: report pre-existing bugs or unmentioned behavior as follow-ups instead of fixing them, implement the most directly supported reading of an ambiguity and state that assumption, commit tests only where the task or repo convention calls for them, but still implement every requested behavior completely.
- **Searches less at low effort**, may answer from memory on half-recognized names. For fast-moving topics or accuracy-critical facts: a name it doesn't confidently recognize, or one from a fast-moving field, is the thing to search, using the name as the user wrote it; familiarity is not a reason to skip the search.
- **Safeguard false positives:** "does this compile" misfires more than "are there any bugs in this program." Prefer the latter. For a lesser-known programming language, give context on what the language is and how it works.
- **Rewrites whole files for small changes.** For a small edit: minimize tokens used to edit files; surgically edit rather than rewrite when the result is the same.
- **For long deliverables at `xhigh`/`max`,** it can draft the whole thing in its reasoning and again in the reply. Prefer `high`; if higher is used, tell it to spend reasoning on understanding the request and settling structure, not on drafting the full output twice.

## Opus 5.5-specific notes

Anthropic's default choice for most workloads (`models/overview`, 24 Sep 2026). Replaces Opus 5 at a lower price, runs more than 30% faster and usually finishes with fewer tokens. Performs best given the complete task specification up front and left to run. The first group below is new or changed on `prompting-claude-opus-5-5` (24 Sep 2026). The second group is carried over from the Opus 5 page (16 Sep 2026): Anthropic says Opus 5 prompts carry over unchanged, but does not restate these quirks for 5.5, so treat them as likely rather than confirmed.

New or changed for Opus 5.5:
- **Default effort is `medium`, not `high`.** Start at `medium`, set the level explicitly, and flag the level a task suggests rather than carrying over a setting used on Opus 5. Effort names don't carry across models: "Claude Opus 5.5 at medium matches or exceeds Claude Opus 5 at high on coding and knowledge-work evaluations, and on several coding evaluations low comes close to it at much lower cost." So a task that needed Opus 5 at `high` usually needs Opus 5.5 at `medium`. At a given level it thinks more per turn than Opus 5, especially at `xhigh` and `max`. To get less thinking, lower the effort first; that works "more reliably than prompt instructions do." 
- **Thinking is always on.** Drop instructions like "think carefully before answering" in chat or system prompts: "The model decides for itself how much to think." Instructions written as a substitute for thinking no longer earn their place; for a cheap run, ask for `low` effort instead.
- **Long unattended runs can stop early with a status report.** It sometimes ends a turn mid-task. For agentic work, ask it to keep a to-do list and continue until every item is done, and have the caller treat a text-only reply as a report, not proof of completion (and stop after two or three automatic continuations rather than looping). A prompt for an unattended agent can name the four ways it ends early (a summary announcing a next step with no tool call, an offer to continue unless the user objects, a list of decisions when none blocks the work, treating a milestone as a place to report) and tell it to put any such note "in the same message as your next tool call and carry on with whatever does not depend on the user's answer."
- **Gets to work quickly on loosely specified tasks.** For work spread across email, documents, spreadsheets or records, tell it to explore first: "Before taking any action, explore broadly with tool calls: list and open the emails, documents, spreadsheet tabs and records across the available apps that could be relevant to this task, including ones the task does not explicitly mention, and use what you find." Anthropic measured noticeably more tasks done correctly with it, at both `medium` and `max`, for slightly more tool calls.
- **Progress updates follow instructions.** For more frequent or predictable updates, say so in the prompt; "the model is responsive to such instructions." If it may need to hand the user something verbatim mid-turn (a code snippet), give it a simple message tool and tell it to reserve that tool for such content.
- **Multi-turn chat: it sometimes goes back over an earlier answer while working on a new message.** If that is unwanted, say to answer the new message and leave earlier answers alone unless asked (this also stops it correcting earlier mistakes, so only add it when the trade is worth it).
- **Pasted material is safer when fenced.** It resists instructions hidden in copied-in content best when that content sits inside tags carrying a random ID and the prompt explains the convention, so a rewrite that includes pasted documents should wrap them that way.
- **Name a tool when one applies.** A tool call can no longer be forced, so a prompt that depends on a particular tool should say when to use it.
- **Images and charts:** even at `low` it reads dense charts better than Opus 5 did at its highest setting, so image-handling scaffolding written for Opus 5 can usually go.
- **Design and visual output:** "avoid a generic AI look" only swaps one default for another. Name the specific patterns to avoid instead.
- **Safeguards:** biology safeguards match Fable 5.1's and are new since Opus 5. "Finding vulnerabilities in source code is allowed. High-risk dual-use cybersecurity activities are not." A security prompt should frame the work as finding and fixing flaws in named code.
- **Do not ask it to reproduce its internal reasoning in the reply.** A new safeguard category (`reasoning_extraction`) declines that. Ask for a short rationale or the key considerations instead.
- **Multi-agent timing:** it pays close attention to elapsed time, so a prompt that coordinates subagents can state the time budget and have progress lines report time used (for example `elapsed 340s / 1200s`).

Carried over from Opus 5:
- **Response length and document length are two separate things to tune, and effort doesn't do either.** Lowering effort reduces thinking, not visible response length. For shorter conversational answers, say so directly: keep responses focused, brief, and concise, keep disclaimers short, give a high-level summary unless depth is asked for. In a long prompt, add a short conciseness reminder near the end as well. Separately, for anything written to disk (reports, docs, summaries): match length to what the task needs, cover the substance, no filler sections, redundant summaries or boilerplate.
- **Narrates readily during agentic work**, and per-message output in agentic sessions runs long. For a quieter agent, describe the cadence: one sentence before the first tool call, a brief update only when something important is found or the approach changes, and a final message whose first sentence answers "what happened" or "what did you find". To tune narration up instead, describe what updates should look like and give positive examples.
- **Over-verifies by default.** It checks its own work without being told to, so "double-check your answer," "re-verify before responding," "add a final verification step," or subagent-based double-checking compound with what it already does and waste tokens; drop those instructions rather than adding them. Likewise "only report high-severity issues" or "be conservative" in a review prompt makes it under-report; ask it to report everything and filter separately.
- **Narrates its own corrections.** For user-facing work, ask it to only flag a correction when the error would change the user's code, conclusions, or decisions, state it briefly, and otherwise fix it silently.
- **Delegates to subagents readily.** To limit it: delegate only large, genuinely independent, parallelizable tracks (a wide multi-file investigation), not work doable in a handful of tool calls, never to verify its own work, and use one subagent rather than several when one suffices.
- **Can widen scope on its own initiative.** For narrow scope: deliver what was asked at the intended scope, make routine judgment calls itself, check in only when readings would lead to materially different work, say in a sentence if the request seems mistaken or a better approach exists and then continue as asked, finish the whole task, and stop short of actions clearly beyond the ask.
- **Office and document work:** strong on multi-sheet spreadsheets and slide decks; name any specific style or template it must follow.
## Sonnet 5-specific notes

Particular strengths in coding and agentic tasks, performs well out of the box on prompts written for Claude Sonnet 4.6. Quirks worth encoding:

- **Calibrates response length to task complexity itself**, usually no length instruction needed. If a product needs a specific length or style regardless, say so ("provide concise, focused responses, skip non-essential context, keep examples minimal"); positive examples of the wanted concision beat prohibitions.
- **Default effort `high`; `xhigh` for the hardest coding/agentic work.** Respects effort strictly at the low end: at `low`/`medium` it scopes tightly to the ask and can under-think a moderately complex task. Prefer flagging a higher effort; if effort must stay low, add "This task involves multistep reasoning. Think carefully through the problem before responding."
- **Follows instructions literally**, especially at lower effort: it won't generalize an instruction from one item to the rest, or infer requests you didn't make. State scope explicitly ("apply this to every section, not just the first").
- **More agentic by default**, reaches for tools and self-verification readily, and gives good progress updates on its own; remove scaffolding that forces interim status messages. If tool use matters (for example web search), say when and why to use the tool. If update length or content is off, describe what updates should look like with an example.
- **Tone may shift on long-form writing.** If a specific voice matters, state it (for example "use a warm, collaborative tone, acknowledge the user's framing before answering").
- **On open-ended design/frontend briefs, settles into one default visual style.** Generic bans just shift it to another fixed look. Either give a concrete visual spec (palette hexes, typography, radius, layout, motion), or ask it to propose several distinct directions (background hex, accent hex, typeface, one-line rationale) and have the user pick one before building.
- **Review prompts:** "only report high-severity issues," "be conservative," or "don't nitpick" lowers recall. Ask it to report every issue with a confidence and severity so filtering happens separately, or give a concrete bar ("report any bug that could cause incorrect behavior, a test failure, or a misleading result; omit only pure style or naming nits").
- **Front-load the task.** For coding work, state the task, intent and constraints fully in the first message; specs drip-fed over several turns cost more tokens and sometimes quality.

## Haiku 4.5-specific notes

Anthropic publishes no Haiku 4.5 prompting page (checked 16 September 2026, see the verification note at the top). Rewrites for Haiku 4.5 rely on the general principles above. The only Haiku-specific points in the official pages read this pass:

- **Covered by the general techniques.** The best-practices page lists Claude Haiku 4.5 among the current models its techniques apply to. Nothing in it names a Haiku-only quirk to prompt around.
- **Has context awareness.** Haiku 4.5 tracks its remaining context window. For an agentic prompt in a harness that compacts context or saves state to files, say so, so it doesn't wrap up early as the limit approaches: keep working, save progress and state before the context refreshes, don't stop a task early for budget reasons.
- **Has no effort setting.** Haiku 4.5 is absent from the effort parameter's supported-model list, so never write an effort level into a Haiku prompt or suggest one.

## What NOT to over-apply

Not every messy prompt needs XML tags, a role, and five examples. A two-sentence request just needs to be clear and specific. The job is to make the ask unambiguous and complete, not to maximize technique count. Match structure to the complexity of the underlying task. The same goes for the three guardrails: add uncertainty permission, quoting, format templates, or confidentiality lines only where the task actually carries that risk.
